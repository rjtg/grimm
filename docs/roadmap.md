# Roadmap

Every milestone ends with an executable demo and regression tests. Milestones describe capabilities, not mandatory features for every game.

| Milestone | Scope | Acceptance demo |
|---|---|---|
| M0 Architecture Foundation | All core boundaries, minimal semantic messages, stub engine/adapter/renderer loop, dependency tests | End-to-end action -> engine -> adapter -> renderer -> input -> engine |
| M1 Classic CYOA | Authored graph, choices, conditions/effects, authored text adapter, CLI, save/load | Play `The Last Witness` through multiple endings offline |
| M1.5 World Modeling & Dogfooding | Build a second independently authored test story; exercise stable characters/locations across different scenes; diagnose narrative deadlocks (CYOA-09); capture authoring friction | Play three distinct scenes at one location, with state-driven choices and at least three endings; publish authoring findings |
| M1.75 Temporal Foundation | Optional deterministic world clock, timed decisions and timeout consequences, authored time advancement, pause/resume and save/load semantics | Play a short scripted timed-choice scenario with manual/fake clock, timeout branch and reliable deterministic replay; untimed M1 stories unchanged |
| M1.8 Narrative Flow & Presentation Gating | Narrative-only presentation segments, host/renderer completion acknowledgement, explicit interaction readiness, bounded engine-owned continuation and player-paced CLI fallback | A storytelling segment finishes before a timed choice becomes available; reading/camera delay does not consume its deadline, and a narrative-only scene advances without a fake choice |
| M2 Interactive Scene Foundation | State-changing choices that can remain in one narrative scene, reveal/replace further offers, and preserve one **scene-completion deadline** across repeated interactions, distinct from a classic choice-selection deadline; optional action execution durations lock new gameplay input while the situation deadline continues; deterministic bounded checking | Play `The Locked Room`: investigate drawers and fireplace, acquire a keyring, attempt several wrong keys, find a metal bar, then choose a timed escape/failed rescue; choices reveal choices without resetting the deadline; trying a key or forcing the door enters a visibly busy state, blocks other gameplay input for an authored duration, and may lose to the running timeout; demo an interrupted in-progress action and state-dependent failure transition |
| M3 Inventory, Puzzles & Character State | Optional persistent items and ownership, authored combinations, puzzle state and typed/validated character attributes (e.g. strength, knowledge, trust, skills) expressed as conditions/effects; no universal verb API | A MacGyver-style authored puzzle has multiple solutions; collected items and RPG-like attributes unlock different scene choices, consequences and save/load branches; combination/crafting durations are visibly demonstrated |
| M4 Narrative Adventure | Combine explorable interconnected locations, repeatable interactions, local puzzles and scene-bound Telltale-like consequential decisions. LucasArts-like investigation and item puzzles feed authored, cinematic CYOA branches; bounded playability checking supports revisiting scenes | A small semi-linear adventure with multiple locations, two linked puzzles, a persistent scene-completion deadline, an independent Telltale-style choice deadline, timed action execution and multiple narrative endings where earlier exploration changes later decisions |
| M5 Graphic Adventure Presentation | Visual scene/room presentation, visible hotspots representing **currently offered choices**, inventory/character views and synchronized M1.8 dialogue/animation presentation; same canonical engine, no hard-coded Inspect/Use/Talk action taxonomy | Deliver an authored graphic-adventure game with scene assets/hotspots mapped to engine choices, compatible renderer capability checks and action-duration synchronization; if the game explicitly ships both text and graphic presentations, verify matching gameplay outcomes |
| Later: Dynamic Narrative / Story-RPG | Optional provider-neutral runtime proposals from human DM, authored tools, rules or LLM; validated graph extensions, open narrative frontiers, persistence and replay | A live human DM extends an ongoing session with valid choices and authored scenes while existing adventure rules remain unchanged |
| Later: Free-text Input, NPC Agency & Narrative Direction | Optional intent resolution, NPC planning and director proposals, introduced only once the authored narrative/adventure model is understood | Separate opt-in demos; baseline authored games remain fully playable offline |

The milestone numbers beyond M5 are **proposed planning labels**, not accepted API or schema commitments. The older M3 Free Input / M4 Dynamic Narrative / M5 NPC Agency / M6 Narrative Direction / M7 Visual Presentation schedule is superseded by the *capability-first* progression above. The capabilities are deferred, not cancelled.

## Product direction: choices are the common interaction model

GRIMM supports both **Telltale-style authored narrative scenes and consequential decisions** (including presentation gating and timed pressure) **and LucasArts-style puzzle/exploration gameplay** (inspect/search places, discover/take items, try alternatives, combine objects and unlock options). Optional **RPG-style character statistics** (attributes, skills, relationships, checks, resources) use the same conditional-choice/effect machinery. Character attributes are game-authored state, not a mandatory RPG ruleset or a new player-input syntax.

**Do not implement a fixed LucasArts verb API** (`Inspect`, `Use`, `Take`, `Combine`, etc.) as the canonical player action model. A scene exposes meaningful, author-defined choices based on current world/inventory/character state. An offered choice is an executable capability: it can change state **without leaving the scene**, reveal new choices or content, consume game/world time or a declared action cost, or transition to another narrative scene. A renderer may display the same choices as numbered text, dialogue choices, clickable hotspots or contextual inventory combinations; presentation does not invent new gameplay actions.

The **scene** represents an ongoing narrative situation; its **current interaction offers** are a projection of state and can change after every action. A room/location is a persistent world context, **not** a scene or graph node. Repeating a scene interaction must not automatically replay required presentation or reset an active deadline. **Optional authored action execution duration** is different from a decision deadline or fictional world-time advance: after a choice is accepted the engine may enter a canonical **action-in-progress** phase, new gameplay choices are unavailable until completion/interruption, and the scene's previously active deadline continues to count down. The host supplies elapsed-time observations; it may display progress and decline new gameplay input, but never sleeps/blocks inside the engine. A timeout can beat completion and the engine alone decides whether effects/transition commit; an action must not become a free pause or restart a deadline. A single time-critical situation may contain several exploratory/failed attempts before success or an authored timeout; effects and exactly-once resolution are engine-authoritative. Define carefully how revision-scoped actions and M1.8 readiness work when the available choices change in place.

Puzzle/story graph validation must handle **node + relevant state**, not merely static edges. Check valid references, reachability of intended interactions, executable exits or intentional endings, and state-dependent deadlocks. Keep explicit bounded/inconclusive analysis; do not claim exhaustive puzzle solvability or globally require that every arbitrary RPG state reaches a fixed ending.

## Games are concrete compositions, not renderer-neutral graphs

A **playable game** is a concrete composition of GRIMM's narrative engine, its authored narrative/rule definition, its actual game/runtime and rendering implementation, required presentation assets/bindings, and any other game-specific systems. **Two integration directions are possible:** a standalone GRIMM-led game whose composition selects/loads a concrete renderer, or a Bevy/other host-led game that already owns its renderer/main loop and embeds GRIMM **only for narrative events**. No single game-definition entry point or dependency direction is mandated yet.

**Do not model game compatibility as merely “this renderer supports 3D, therefore it can play this 3D game.”** Even a capable Bevy renderer lacks the game's particular rooms, cameras, models, character rigs, interaction hotspots and authored choreography unless those are explicitly provided and wired together. Neither a text graph nor a general renderer capability list is a complete game.

The headless **GRIMM engine** owns its canonical **narrative state**, temporal semantics, rule validation and committed narrative choices; it does not acquire a Bevy dependency or load game-specific assets. **An external host may own other world state, simulation, movement and rendering.** The surrounding game's composition root wires the concrete components in either direction. Narrative outcomes and host world changes need an explicit ownership/coordination boundary. Multi-renderer variants, if ever useful, must be explicit game-authored compositions rather than automatic playback of an arbitrary graph.

M2–M4 may continue using today's explicit CLI composition as their complete playable text games. M5 should deliver a fully authored graphical game with the actual renderer, assets and bindings. **Investigate embedding** by a small host-owned world-trigger → GRIMM narrative choice → host-world consequence spike; assess whether it merits a supported integration mode and what contract it requires, rather than mandating embedding before evidence. Use those concrete findings to decide which packaging and API contracts are shared across entry points; see [game composition questions](open-questions.md#game-composition-renderer-origin-and-packaging) and [embedded host questions](open-questions.md#host-integration-standalone-game-versus-embedded-narrative-engine).

## Milestone sequencing and authoring evidence

M0–M1.8 are implemented and remain supported. **M2** completes the transition from classic text CYOA to *stateful interactive scenes* by dogfooding a tightly authored room escape. Reuse existing choices, conditions and effects wherever possible. Make new authoring primitives only where the demo exposes real friction. **M3** adds minimal inventory/item and optional character-stat conventions validated by a genuinely playable combination puzzle; **M4** combines those pieces into a semi-linear narrative adventure; **M5** presents the same authored gameplay graphically. **Every milestone must demonstrate every introduced gameplay capability through a genuinely playable, end-to-end demo story**, with at least one success path and relevant failure/timeout paths where applicable. Do not count isolated protocol fixtures or unit tests as the acceptance demo. Document exact player input steps, state-sensitive outcomes, action-busy behavior and regression checks; previous demo games must still work. Every milestone also includes automated tests, bounded playability diagnostics and an authoring/playtest report.

Human DM / LLM runtime graph editing is a **later optional extension**, not the immediate next milestone. A future **Dynamic Node Provider Boundary** should be provider-neutral (human author/DM, rules or LLM) and engine-validated. Its eventual proposal contract, graph frontier semantics and graph checker changes remain questions in [the open-points catalog](open-questions.md). No dynamic graph provider, LLM, open-world simulator, ECS or generic action taxonomy is a prerequisite for M2–M5.

M1.75 establishes a **single temporal model** before stateful interactive scenes and optional future free-text input. It is independent from M1.5's world-entity model and may reuse the lighthouse test game for demonstration without retrofitting it. The core does not poll the wall clock, sleep or own a frontend timer. Host/runtime drivers supply elapsed time explicitly; adapters render player-visible remaining time and frontend readiness. M2–M4 reuse this model for scene-local choices and puzzle consequences; later optional generators/NPCs may react to validated time progression. No background actor or full scheduling engine is required for M1.75.

M1.8 refines the lifecycle established by M1.75: **finishing presentation is not identical to making a choice available**. A narrative segment may stand alone and advance after an authorized completion acknowledgement, while an interactive segment's decision timer must start only after required storytelling and actual offer readiness. A text CLI should allow the player to acknowledge reading before a deadline starts; visual adapters/renderers will later report completion of dialogue, camera movement, animation or other required atmospheric work through the composition root. The engine remains authoritative over all transitions and deadlines; neither completion events nor scene IDs imply a location entity. M1.8 implements the compatible engine/semantic/presentation lifecycle before M2, with replayable timed storytelling demonstrating both paths. No generic cutscene sequencer, full auto-play graph or renderer-to-engine direct dependency is intended.


## Two different deadline semantics: choosing versus concluding

**Choice-selection deadline (classic Telltale / existing M1.75):** The timer bounds **when the player must choose**. A valid choice accepted before expiry resolves the offer, even if the chosen action subsequently takes execution time. Expiry **without a choice** follows an authored no-response/default transition (e.g. silence angers an NPC). Selection, not action completion, is the success criterion. The existing timed-decision feature and legacy saves/stories retain this meaning; do not reinterpret it.

**Scene-completion deadline (authored adventure / M2):** The timer bounds **when an authored scene objective must be achieved**, not when the player makes their first choice. Searching drawers, trying keys and forcing a door are multiple choices inside one ongoing scene, each with optional execution time. Refreshing offers or choosing a promising action does **not** complete the objective, reset the deadline, or guarantee success. A scene deadline may expire while an action is executing, causing an authored *interruption/timeout transition* even if the action would have succeeded after another second. The engine, not a rendering animation, decides completion and timeout ordering.

These are **distinct opt-in policies**; do not overload one `limit_ms` field with an ambiguous meaning or change existing M1.75 behavior. A future scene may use either policy, and combinations require explicit conflict/priority rules rather than implicit timer restarts.

### Interrupted actions and intermediate narrative state

An in-progress action has a canonical identity, declared duration, start/progress, and any explicitly defined **partial/interruption effects**. On a scene-completion deadline the engine evaluates an authored interruption outcome using a deterministic **snapshot at the interruption instant**: elapsed action time, remaining/required duration, available scene time, current committed facts, and relevant RPG-style attributes such as `suspicion`. Do not silently apply effects intended for successful action completion. A check can select one of multiple authored transitions based on these values, and its input/outcome must be replayable.

Example: the detective enters while the player is still hiding a weapon. Whether the player is caught can depend on the hiding progress when the scene deadline fires **and** the already committed `suspicion` stat. If the weapon is nearly hidden, the authored scene may allow a better deception outcome; if it was barely moved, the detective immediately discovers it. The precise formula and any optional RNG/check mechanics belong to game-authored rules and will be specified with tests, not hard-coded into the engine. This is a **conditional authored transition from a partial action state**, not generation of a new node.

The M2 acceptance demo must demonstrate both deadline policies separately, including silence causing a narrative response, plus a door/hidden-object objective interrupted mid-execution with differing authored outcomes based on progress/state. Time advancement must split at the earliest relevant event boundary (completion vs scene expiry); exact ties, simultaneous events, partial effects, pauses, and save/restore require deterministic precedence and atomic resolution. A later M3 demo demonstrates the same mechanism with RPG attributes. The full visual representation remains M5; text feedback suffices for M2.

## Action completion and externally supplied time

**GRIMM never advances a clock autonomously**, polls wall time or sleeps. It processes explicit, revision-scoped host inputs. Distinguish **elapsed real time observed by a host**, **authored execution duration**, **fictional world-time cost** and **committed story consequences**. At choice acceptance (T0), GRIMM validates the action and computes a **provisional, authored planned outcome** (e.g. success *if completed without interruption*, failure, or conditional branch), its execution duration and a semantic presentation cue. This immediate response allows the renderer to play an appropriate success-attempt or failure-attempt animation. The planned result is not yet the committed result. The action is then executed/presented for its authored duration. The host reports completion or interruption with an externally established elapsed-time observation; the engine validates the action identity/revision, duration/ordering and deadline implications **before committing successful effects and any fictional time cost**. The renderer may originate a presentation-complete acknowledgement, but the host/composition root must correlate and validate it: the renderer is not trusted to declare success or rewrite canonical time.

An authored five-second action should display the **engine-selected planned-outcome animation** for a five-second interval, but animation completion is **not sufficient evidence** that the planned success became a canonical success. The host provides timing information; the engine applies deterministic rules and remains independently replayable with recorded inputs. A five-second completed action should not implicitly cause five additional seconds of presentation after its resolved outcome.

**Drawer example:** at T0 the player selects `open_drawer`; GRIMM authorizes a planned success if uninterrupted, a five-second execution duration, and a drawer-opening presentation cue. The renderer plays that animation immediately. At T5 the host's elapsed observation lets GRIMM commit `drawer_open = true`, expose the keychain choice and publish the authoritative visual state. An interruption before T5 instead resolves an authored alternative; no success effect leaks early.\n\n**Door example:** a scene's ten-second real-time completion deadline begins at readiness. At t=6s GRIMM validates the player's five-second door-breaking choice and reports a **planned success if uninterrupted**, along with the corresponding five-second forcing animation; the scene expiry at t=10s interrupts it at 4/5 execution progress, before its nominal finish at t=11s. The outcome is an authored interruption/failure transition, potentially conditioned on partial progress or committed stats. A renderer/host must report expiry promptly for a responsive interruption. Even if the host reports only a late action completion at t=11s with a five-second interval, the engine must reconcile the recorded time interval against the earlier t=10s scene boundary and **reject success**; no completion callback may bypass expiry. A renderer acknowledgement like “choice X completed; 5s elapsed” is a possible host-level transport message, **not** an authoritative command to commit action success or advance every clock by five seconds.

**Decision timeouts remain distinct:** in classic Telltale selection deadlines the player only needs to choose before expiry; unanswered dialogue has an authored consequence. Scene-completion deadlines instead require a finished objective and can interrupt intermediate actions. Neither implies an always-running core simulator. For *idle* real-time expiry or events occurring during an animation, the host must still supply observed elapsed time/events without waiting for a choice to complete. Authored fictional world time can be advanced by a validated action-resolution cost, as in M1.75, independently of wall-clock elapsed time.

Action execution and pre-choice M1.8 presentation gating are different lifecycles. During action execution, reject conflicting gameplay choices but retain host/session pause/save/quit controls. Pauses, disconnect, save/load, late/duplicate completion, exact-boundary ordering, partial effects, progress and host clock observation policies require explicit M2 design and tests. The headless core must never wait on the renderer or own the monotonic clock. See [open questions](open-questions.md).

## Deferred generation and presentation questions

Generating new nodes is distinct from altering how committed content is rendered. When future dynamic adventures are introduced, external human DM, rule-based and optional LLM providers must use the same validated proposal boundary; the engine owns canonical state and commit. Whether stylistic generative presentation is worth a separate opt-in adapter remains an open question, **not a milestone requirement**. See [open questions](open-questions.md#dynamic-narrative-provider-and-future-generation).

## Delivery rules
- Each requirement has tests and acceptance criteria, including real playable demos.
- The classic game remains playable after every milestone; new mechanics stay opt-in.
- Later features do not become mandatory dependencies for earlier experiences.
- Unknown future APIs remain deliberately unspecified.
