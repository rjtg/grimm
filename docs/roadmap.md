# Roadmap

Every milestone ends with an executable demo and regression tests. Milestones describe capabilities, not mandatory features for every game.

**Current M2 design focus:** authored, choice-driven **LucasArts-style puzzles/exploration** and **Telltale-style staged narrative decisions**, with at most lightweight optional RPG-like state checks (`strength`, `dexterity`, `suspicion`). All movement between narrative contexts is explicitly authored through choices; **no embedded Bevy/3D host, open-world traversal, host-controlled free movement, complex RPG framework or generated story system belongs to M2 scope**. External host integration remains a later separate question. M2 must demonstrate its mechanics in a complete playable room-escape example, not just isolated protocol fixtures.

**M2 namespaced authored IDs (M3 indexes/validates):** By default, **the authored story-node name is the namespace**; local action and `cue`/animation cue identifiers are normalized to **lowercase ASCII snake_case** and emitted as unique qualified IDs (e.g. `interrogation_miller.tell_truth` versus `interrogation_smith.tell_truth`). Allow an explicit stable namespace override when a node is renamed/refactored but asset bindings must remain unchanged. M2's compiler rejects effective-ID duplicates; M3 provides detailed duplicate and cross-reference diagnostics, including collisions **after normalization**, reporting both source locations rather than silently rewriting/suffixing IDs. Repeated executions inside one node reuse the same ID. Both renderers treat the qualified ID as an opaque lookup key; the ID's namespace does **not** tell the renderer to inspect the story graph. Exact DSL syntax is not fixed here.

**Cue pacing across renderers:** An authored Cue Sheet may contain multiple **ordered** `cue` IDs to mark meaningful narrative beats, not merely animations. The text renderer may show one beat/paragraph at a time and pace it with an estimated reading duration derived from the concrete text or user-selected/manual advance; the graphical renderer may play a distinct scene, camera or audio sequence per beat. Both must preserve the authored cue order. **GRIMM never computes reading delays or visual shot timings**, and optional scene timers do not consume time while any required cue is being presented. After all cues finish, the renderer enables `actions` and starts/resumes the stated timer baseline. The renderer may allow skip/instant text access without changing story rules.

**Same-repository example games and shared IDs:** Keep the concrete M4 text game and M5 graphical adaptation as example applications in this GRIMM repository (e.g. under `examples/`); both load **the exact same GRIMM story script**. Given the same action/time inputs, GRIMM produces the same Cue Sheets and canonical gameplay outcomes. The only difference is the renderer and its assets: M4 owns a lookup of cue IDs to written narrative/dialogue and action IDs to visible option labels; M5 interprets those same IDs as visuals/animations, voices, subtitles and clickable/menu options. The renderer's input always reports the shared `game_action` action ID; it never feeds renderer-specific wording to GRIMM. **Concrete text, dialogue-line wording, subtitle text, audio files and descriptive option labels live with the renderer/game assets, not in the GRIMM game-rule script.** The engine knows the authored *meaning* of an ID through its rules, not how it is phrased or staged. No new renderer-independent dialogue text format or cross-game asset registry is required.

**Milestone ownership:** M2 establishes namespaced, stable effective cue/action IDs as part of the DSL/Cue Sheet handshake. M3 adds a machine-readable index, collision diagnostics with source references, linting, bounded state exploration and sample renderer-manifest checking. M4 and M5 then use that same index for their complete text/graphics example asset coverage. M3 need not produce a new full game.

**Roadmap decision:** The former **M3 Inventory/Puzzles/Character State** scope is cancelled. **M3 Story Authoring & Validation Toolchain** is now the proposed successor: tooling, not new gameplay primitives. M2 remains responsible for a working DSL compiler and basic graph/type checks; M3 makes real game authoring and cross-renderer content coverage practical. The milestone labels **M4** (complete text adventure) and **M5** (graphical adaptation of that **same** adventure) are intentionally preserved. M2 delivers the authoring/runtime foundation; M4 tests real adventure authoring and integration; M5 tests whether the boundary holds with an actual renderer, authored media and an application embedding the GRIMM library. The graphical adaptation must not rebuild or copy the canonical game rules into renderer code. A new engine feature is justified only by a concrete obstacle discovered in the actual game.

**Application composition working direction:** `GRIMM` is the reusable headless Rust library owning the authored game rules/world state and emitting cue sheets. The **concrete game application** owns its selected renderer, its game-specific assets, input and presentation state, and coordinates any renderer-side save with GRIMM's canonical save. A text presentation in M4 and a graphical presentation in M5 may use different renderer implementations to interpret **the same `cue(cue_id)` and `actions`**. M4/M5 examples live in this repository; their exact workspace/example layout remains an implementation choice.

The milestone numbers beyond M5 are **proposed planning labels**, not accepted API or schema commitments. The older M3 Free Input / M4 Dynamic Narrative / M5 NPC Agency / M6 Narrative Direction / M7 Visual Presentation schedule is superseded by the *capability-first* progression above. The capabilities are deferred, not cancelled.

## Product direction: choices are the common interaction model

GRIMM supports both **Telltale-style authored narrative scenes and consequential decisions** (including presentation gating and timed pressure) **and LucasArts-style puzzle/exploration gameplay** (inspect/search places, discover/take items, try alternatives, combine objects and unlock options). Optional **RPG-style character statistics** (attributes, skills, relationships, checks, resources) use the same conditional-choice/effect machinery. Character attributes are game-authored state, not a mandatory RPG ruleset or a new player-input syntax.

**Do not implement a fixed LucasArts verb API** (`Inspect`, `Use`, `Take`, `Combine`, etc.) as the canonical player action model. A scene exposes meaningful, author-defined choices based on current world/inventory/character state. An offered choice is an executable capability: it can change state **without leaving the scene**, reveal new choices or content, consume game/world time or a declared action cost, or transition to another narrative scene. A renderer may display the same choices as numbered text, dialogue choices, clickable hotspots or contextual inventory combinations; presentation does not invent new gameplay actions.

The **scene** represents an ongoing narrative situation; its **current interaction offers** are a projection of state and can change after every action. A room/location is a persistent world context, **not** a scene or graph node. Repeating a scene interaction must not automatically replay required presentation or reset an active deadline. **Optional authored action duration** is resolved immediately when GRIMM receives the choice and host-correlated selection time; a known deadline can truncate that duration and select a different authored outcome. GRIMM commits the outcome once and supplies its prescribed animation/narrative presentation. New gameplay inputs remain unavailable until the presentation is finished and M1.8 interaction readiness is satisfied. No running action state, later success callback or action-time ticking is needed. A single time-critical situation may contain several exploratory/failed attempts before success or an authored timeout; effects and exactly-once resolution are engine-authoritative. Define carefully how revision-scoped actions and M1.8 readiness work when the available choices change in place.

Puzzle/story graph validation must handle **node/context + relevant state + time**, not merely static edges. Follow only authored transitions; **never assume implicit return to earlier scenes or nodes**. For a locked door reached without a key, a Telltale-style narrative needs an explicit `leave_and_search_for_key` choice to reach the key rack. A host-led RPG can end the door interaction and return to external exploration; the host may later trigger a key-rack interaction and eventually the door again. The checker must not invent those host movements or infer them from graph history. Diagnose proven trapped nonterminal states, accept intentional endings/timeouts, and report bounded or unknown-host reachability as *inconclusive* rather than claiming exhaustive solvability.

## Games are concrete compositions, not renderer-neutral graphs

A **playable game** is a concrete composition of GRIMM's narrative engine, its authored narrative/rule definition, its actual game/runtime and rendering implementation, required presentation assets/bindings, and any other game-specific systems. **Two integration directions are possible:** a standalone GRIMM-led game whose composition selects/loads a concrete renderer, or a Bevy/other host-led game that already owns its renderer/main loop and embeds GRIMM **only for narrative events**. No single game-definition entry point or dependency direction is mandated yet.

**Do not model game compatibility as merely “this renderer supports 3D, therefore it can play this 3D game.”** Even a capable Bevy renderer lacks the game's particular rooms, cameras, models, character rigs, interaction hotspots and authored choreography unless those are explicitly provided and wired together. Neither a text graph nor a general renderer capability list is a complete game.

The headless **GRIMM engine** owns its canonical **narrative state**, temporal semantics, rule validation and committed narrative choices; it does not acquire a Bevy dependency or load game-specific assets. **An external host may own other world state, simulation, movement and rendering.** The surrounding game's composition root wires the concrete components in either direction. Narrative outcomes and host world changes need an explicit ownership/coordination boundary. Multi-renderer variants, if ever useful, must be explicit game-authored compositions rather than automatic playback of an arbitrary graph.

M2–M4 may continue using today's explicit CLI composition as their complete playable text games. M5 should graphically adapt the **same M4 authored game** with its actual renderer, assets and bindings. **Investigate embedding** by a small host-owned world-trigger → GRIMM narrative choice → host-world consequence spike; assess whether it merits a supported integration mode and what contract it requires, rather than mandating embedding before evidence. Use those concrete findings to decide which packaging and API contracts are shared across entry points; see [game composition questions](open-questions.md#game-composition-renderer-origin-and-packaging) and [embedded host questions](open-questions.md#host-integration-standalone-game-versus-embedded-narrative-engine).

## Milestone sequencing and authoring evidence

M0–M1.8 are implemented and remain supported. **M2** completes the transition from classic text CYOA to *stateful interactive scenes* by dogfooding a tightly authored room escape. Reuse existing choices, conditions and effects wherever possible. Make new authoring primitives only where the demo exposes real friction. **M3 targets authoring validation/indexing rather than an inventory or RPG framework**, because M2 already covers those lightweight gameplay needs; **M4** combines those pieces into a semi-linear narrative adventure; **M5** presents the same authored gameplay graphically. **Every gameplay milestone must demonstrate introduced gameplay capabilities through an end-to-end playable demo; tooling-only M3 must validate existing playable content and illustrative manifests**, with at least one success path and relevant failure/timeout paths where applicable. Do not count isolated protocol fixtures or unit tests as the acceptance demo. Document exact player input steps, state-sensitive outcomes, action-busy behavior and regression checks; previous demo games must still work. Every milestone also includes automated tests, bounded playability diagnostics and an authoring/playtest report.

Human DM / LLM runtime graph editing is a **later optional extension**, not the immediate next milestone. A future **Dynamic Node Provider Boundary** should be provider-neutral (human author/DM, rules or LLM) and engine-validated. Its eventual proposal contract, graph frontier semantics and graph checker changes remain questions in [the open-points catalog](open-questions.md). No dynamic graph provider, LLM, open-world simulator, ECS or generic action taxonomy is a prerequisite for M2–M5.

M1.75 establishes a **single temporal model** before stateful interactive scenes and optional future free-text input. It is independent from M1.5's world-entity model and may reuse the lighthouse test game for demonstration without retrofitting it. The core does not poll the wall clock, sleep or own a frontend timer. Host/runtime drivers supply elapsed time explicitly; adapters render player-visible remaining time and frontend readiness. M2–M4 reuse this model for scene-local choices and puzzle consequences; later optional generators/NPCs may react to validated time progression. No background actor or full scheduling engine is required for M1.75.

M1.8 refines the lifecycle established by M1.75: **finishing presentation is not identical to making a choice available**. A narrative segment may stand alone and advance after an authorized completion acknowledgement, while an interactive segment's decision timer must start only after required storytelling and actual offer readiness. A text CLI should allow the player to acknowledge reading before a deadline starts; visual adapters/renderers will later report completion of dialogue, camera movement, animation or other required atmospheric work through the composition root. The engine remains authoritative over all transitions and deadlines; neither completion events nor scene IDs imply a location entity. M1.8 implements the compatible engine/semantic/presentation lifecycle before M2, with replayable timed storytelling demonstrating both paths. No generic cutscene sequencer, full auto-play graph or renderer-to-engine direct dependency is intended.


## Two different deadline semantics: choosing versus concluding

**Choice-selection deadline (classic Telltale / existing M1.75):** The timer bounds **when the player must choose**. A valid choice accepted before expiry resolves the offer, even if the chosen action subsequently takes execution time. Expiry **without a choice** follows an authored no-response/default transition (e.g. silence angers an NPC). Selection, not action completion, is the success criterion. The existing timed-decision feature and legacy saves/stories retain this meaning; do not reinterpret it.

**Scene-completion deadline (authored adventure / M2):** The timer bounds **when an authored scene objective must be achieved**, not when the player makes their first choice. Searching drawers, trying keys and forcing a door are multiple choices inside one ongoing scene, each with optional execution time. Refreshing offers or choosing a promising action does **not** complete the objective, reset the deadline, or guarantee success. A scene deadline may expire while an action is executing, causing an authored *interruption/timeout transition* even if the action would have succeeded after another second. The engine, not a rendering animation, decides completion and timeout ordering.

These are **distinct opt-in policies**; do not overload one `limit_ms` field with an ambiguous meaning or change existing M1.75 behavior. A future scene may use either policy, and combinations require explicit conflict/priority rules rather than implicit timer restarts.

### Known deadlines and arithmetic partial progress

When a scene deadline falls within a selected action's authored duration, GRIMM can compute the **effective attempted duration** at choice selection. It may use that arithmetic fraction and committed attributes (e.g. `suspicion`) to choose an authored conditional transition for a detective entering before a weapon is hidden. This is **one deterministic choice resolution**, not a continuously running in-game action or a time-observed interruption snapshot.

For a five-second door action selected at T=6s with a T=10s scene deadline, GRIMM chooses the four-second attempted-door presentation and corresponding failure transition immediately. Renderer presentation finishes before new choices activate; the underlying narrative outcome does not wait for a later callback. Exact ties, time unit precision, host timestamp validation and real-time idleness remain M2 design/test questions.

**Concrete M2 illustrative acceptance trace:** [The Locked Room — Cue Sheets and Game Actions](milestones/m2-cue-sheet-reference.md) shows complete renderer messages and time accounting, including `open_drawer`, `take_keychain`, wrong/right keys, repeated `break_door` with `door_damage += character_strength`, threshold-based cues, conditional `squeeze_through` and `timeout`. Implementers should make the authored DSL express the example without hardcoding puzzle mechanics. The trace is a behavioral fixture, **not a fixed DSL grammar or serialized protocol**.

**Mini-games within the DSL:** an authored story node/narrative context can contain an entire small interactive challenge, not just one choice or one animation. For example, the [locked-room reference](milestones/m2-cue-sheet-reference.md) can keep `door_damage`, `has_keychain`, door checks, time costs and multiple alternative solutions inside a single authored context and emit successive Cue Sheets. Story nodes mainly organize narrative authoring; they do not encode every micro-interaction. **Do not add a separate mini-game engine** or require one graph node per attempted action.

**World state versus renderer state:** M2 `world_state` is GRIMM-owned authored variables; it need not be transmitted in Cue Sheets. Pre-rendered renderers may simply play the IDs; live-rendered renderers interpret the same `cue(cue_id)` cues into their own graphical state. A later full graphical game's save may contain both GRIMM canonical data and renderer-owned presentation data, restored consistently by its game composition. This does not require a new M2 Cue Sheet field or a new M2 save lifecycle.

**Order-sensitive detective test (DSL-13):** besides the timed locked-room fixture, test two initially available, untimed actions `search_crime_scene` and `examine_body`. Searching first while the suspect is present offers `confront_suspect`; examining the body first sets `suspect_present=false`, so a later search only reveals `find_suspect_footprints`. This confirms authored choice order and persistent canonical state change future offers without requiring per-action graph nodes or a timer.

## M2 story DSL — mandatory output

Alongside the Cue Sheet runtime contract, M2 must deliver a **small, readable, documented authored story DSL**. It must express start/end contexts and explicit graph transitions; choice and timeout handlers; `IF/ELSE`-equivalent rules on world state, light RPG stats and `time_passed`; typed global/context-local variables (without mandatory renderer-visibility tags); atomic state updates; authored action durations, timer starts/changes and costs; ordered semantic presentation cues; and conditional action offers. The authored rules produce **one fully resolved Cue Sheet** per input and keep story node transitions private to GRIMM. Existing YAML stories must remain supported.

M2 acceptance includes authored `The Locked Room`, representative invalid DSL examples with actionable diagnostics, basic explicit graph/branch coverage validation, tests for time accounting and committed game state, and documentation showing an author how to write and run the scenario. The implementer **may decide the concrete grammar, parser, Rust types, compilation format and minimal adapter changes**, provided these observable DSL requirements hold. Do not introduce a general-purpose VM, generic game scripting framework, extensive RPG taxonomy or new save lifecycle as a prerequisite. See [DSL-01..DSL-12](requirements.md#m2-authoring-dsl--required-milestone-deliverable).

## M2 Cue Sheet handshake (working design)

An illustrative GRIMM response can be called a **Cue Sheet**: `cue: [enter_corridor, dialog_scene_1]; actions: [A,B,C]; timer: 20s` (with revision). The renderer executes the presentation cues, makes the actions available and starts the timer **after the required presentation**. If the player selects A five seconds later, it returns the equivalent of `[action_selected(A), timer_elapsed(5s)]`. If nobody chooses, the renderer/host reports elapsed expiry and GRIMM chooses the authored timeout result. It then returns the next Cue Sheet. This is a conceptual protocol, not yet a fixed serialized type; no clock polling or rendering dependency enters the core. For a scene-completion budget continuing across choices, refreshes must preserve the existing deadline rather than resetting `timer: 20s` on each response.

## M2 timer and presentation simplification (working design, not fixed schema)

For authored LucasArts/Telltale adventures, treat time as a **game-authoring input** rather than a compulsory realtime simulation. The story can branch using explicit comparisons on a clearly defined `time_passed` value, including authored equality behavior. A choice's authored action duration matches the duration of its associated presented action animation; unrelated fictional world chronology can be normal typed state. For M2 there is no requirement for simultaneous active **choice-selection** and **situation-completion** deadlines, and no new engine-level Pause concept. The host supplies temporal observations without the core reading the wall clock; existing M1.75 pause/save behavior remains backward compatible even if new M2 situations restrict saving at active deadlines or unfinished presentation.

The minimal M2 Cue Sheet conveys `id`, ordered `cue(cue_id)` cues, `actions` and optional `scene_timer` elapsed/total. A mandatory `world_state` field is **not** part of the M2 renderer contract; GRIMM evaluates its internal canonical variables into cues/actions. Concrete wire syntax remains for implementation. GRIMM decides the choices and presentation cues; the renderer determines how to display them. Timing and revisional input-gating must preserve the minimal M1.8 contract. Authoring should cover every executable choice with a deterministic outcome (fallback or exhaustive guards), but exhaustive multi-state puzzle solvability is not an M2 prerequisite.

## Choice-triggered, fully resolved action time (M2)

**A choice is resolved completely when GRIMM receives that choice and its host-supplied selection time.** GRIMM already owns the authored action duration, scene-completion deadline, conditions/effects, interruption rules and successor scenes. It evaluates the entire action interval **arithmetically in one deterministic engine transition** at selection, including any crossing of the scene deadline, and commits the resulting world/narrative facts and next scene or in-scene offers **once**. It emits an authorized **presentation sequence** (with durations and any applicable staged reveal of offers). It does **not** enter a pending game-action state or wait for action-complete/succeeded, periodic elapsed-action ticks or an animation callback to decide success. The renderer reports **input**, never its outcome. The host may report elapsed time when the player *idles without choosing* so existing real-time selection/scene deadlines can still expire, but no action-progress events are needed after an accepted choice.

**Open drawer:** host supplies `open_drawer` selected at T0. GRIMM resolves the five-second authored action immediately: commits `drawer_open = true`, makes `take_keychain` valid in the resulting scene state, and emits a five-second drawer-opening presentation. The renderer plays the animation and keeps next offers hidden/non-interactive until their prescribed presentation has completed and the host acknowledges readiness under the existing M1.8 boundary. The renderer reconstructs the **persistent open drawer** from committed facts after presentation, revisit or save/load; it does not own that state.

**Door deadline:** a scene-completion deadline is at T=10s; the host reports `break_door` selected at T=6s; authored duration is five seconds, nominal completion T=11s. At selection GRIMM determines that the deadline cuts the action at T=10s, i.e. **4/5 seconds into the attempted action**. It immediately commits the authored failure/interruption transition (which may depend on committed stats and calculated partial progress), emits a four-second attempted-door animation followed by the failure presentation, and specifies the next scene/offers. No later renderer callback decides the outcome; partial progress is an arithmetic input to the one transition, not continuously persisted gameplay state.

**Illustration — repeated door-breaking choices with character strength:** GRIMM may retain an authored `door_break_progress` counter across several **separate** executions of the same `break_door` choice. For example, an authored strength-dependent threshold might require **one attempt for a strong character, two for an average character or three for a weaker character**. Each input resolves **once at selection**: GRIMM checks `strength`, previous progress, the action's time cost and the scene deadline, updates the committed progress/result and chooses the semantic presentation. Non-final attempts emit a `try_break_door` cue, retain the scene and (after presentation readiness) reoffer `break_door`; the successful attempt emits `success_break_door`, commits the opened door and advances the story. Authors may distinguish feedback/animation by `strength` or progress (e.g. `try_break_door_weak`, `try_break_door_almost`) to visually signal likelihood of success. These are **illustrative game-authored presentation cues, not built-in engine verbs or universal asset IDs**; game-specific adapters bind them to actual clips. Each attempt consumes its authored effective scene time, and the deadline can still cut a particular attempt short and select a failure branch. **The counter is persistent game state between distinct Choices, not continuously tracked animation progress inside an action.** This interaction is testable as a small M2 example using ordinary state variables; M3 adds formally modeled character stats if needed.

**Distinct timeout policies remain:** an M1.75/Telltale-style **choice-selection deadline** is satisfied when a valid choice is selected in time; silence triggers the authored no-response outcome. An M2 **scene-completion deadline** checks whether an authored objective would complete in time, accounting for sequential action durations. GRIMM updates the authoritative *logical* time as a consequence of each resolved choice (or the deadline cut-off), not by polling or ticking internally. Host-observed real-time timestamps establish player selection/idle time; fictional world-time cost remains a separate authored rule. A new decision clock must not start while the associated presentation is unfinished, retaining M1.8 readiness.

**Important scope:** this model covers *fully authored, sequential choice-based actions* whose relevant consequences can be calculated from the state and time known at selection. True asynchronous external changes during an animation, cancellable actions, live physics, or external host ownership of an object may require a different later integration contract; they must not be smuggled into M2 through a premature action-progress simulator.

M2 tests must show correct outcome at selection, a completed five-second drawer animation with subsequently revealed choices, a five-second door attempt cut to four seconds by a known deadline, idle-time expiry reported by the host, graphical state reconstruction from committed facts and prevention of early choice input. No polling, renderer-success message or in-progress action snapshot is required for the authored action outcome. See [open questions](open-questions.md).

## Deferred generation and presentation questions

Generating new nodes is distinct from altering how committed content is rendered. When future dynamic adventures are introduced, external human DM, rule-based and optional LLM providers must use the same validated proposal boundary; the engine owns canonical state and commit. Whether stylistic generative presentation is worth a separate opt-in adapter remains an open question, **not a milestone requirement**. See [open questions](open-questions.md#dynamic-narrative-provider-and-future-generation).

## Delivery rules
- Each requirement has tests and acceptance criteria, including real playable demos.
- The classic game remains playable after every milestone; new mechanics stay opt-in.
- Later features do not become mandatory dependencies for earlier experiences.
- Unknown future APIs remain deliberately unspecified.
