# M1.75 — Temporal Foundation

## Objective
Implement the smallest *optional*, deterministic temporal foundation for narrative gameplay, before M2 generative presentation. Both time pressure and deliberate passage of fictional time must have clear engine-owned consequences, without introducing background simulation or renderer coupling.

## Prerequisites and boundary contract
- Read `AGENTS.md`, `docs/architecture.md`, `docs/requirements.md`, `docs/roadmap.md`, `docs/story-format.md`, all accepted ADRs and [ADR-0006](../adr/0006-game-time-and-temporal-semantics.md).
- Preserve M0/M1/M1.5 graph, adapter and renderer boundaries; `Engine` does not read wall time or call sleep.
- First draft a focused technical plan for temporal input, deadlines, timeout semantics, and persistence compatibility. Review any changes to accepted architectural boundaries through an ADR.

## Scope
1. **Opt-in world time (TIME-01):** represent authoritative in-game time in a deterministic, serializable form; explicit host/engine time advance. Untimed stories remain unchanged.
2. **Timed interactions (TIME-02):** permit an authored deadline and a validated, deterministic expiry branch or default action. At a given interaction revision, action and expiration must never both commit. Define what occurs if a choice arrives exactly at the deadline.
3. **Action costs (TIME-03):** optionally advance fictional time on selected actions. Enable a minimal temporal condition or time-triggered consequence, with appropriate graph/state validation. Keep world time independent of the decision deadline clock.
4. **Lifecycle (TIME-04):** establish and test when a deadline starts (readiness/presentation acknowledgement), pauses, resumes, and how a pending deadline survives save/load. Choose and document an explicit offline-time policy; do not rely on renderer timing.
5. **Visible countdown (presentation):** provide safe, player-visible deadline information via semantic output and adapt it into a simple CLI indication. The CLI does not decide the result. Do not require real-time animation or an asynchronous framework for the first version.
6. **Demonstration:** a short authored temporal encounter with (a) a player choice before expiry, (b) a timeout consequence when no input arrives, and (c) fictional time advancing via a decision. Can build on the lighthouse playtest but should be independently testable.

## Acceptance criteria
- [x] With a manually controlled/fake host clock, identical input/time sequences produce identical state and output.
- [x] An untimed M1 story behaves identically and requires no ticks.
- [x] A presented interaction has a documented start trigger; no deadline expires merely because a slow frontend is rendering.
- [x] A timely action succeeds; a late action is rejected; a timeout follows its authored, validated consequence.
- [x] Simultaneous action/expiry at the configured boundary has a specified, tested precedence rule.
- [x] Duplicate or repeated expiry/time inputs do not commit a timeout twice.
- [x] Pausing freezes the configured decision timer; resume is deterministic.
- [x] Save/load preserves world time and a pending deadline under a documented offline-time policy.
- [x] An authored action advances world time and changes a later condition/consequence.
- [x] No AI, graphics, system-clock access or timer thread is needed to test engine behavior.
- [x] Existing M0/M1/M1.5 reference stories and regression tests still pass.
- [x] Run `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, plus a scripted CLI demonstration.
- [x] README and story-format documentation explain authoring time limits, fictional-time costs, timeout behavior and compatibility.

## Non-goals
Continuous world simulation, generalized event-scheduling framework, offscreen autonomous NPC actions, free-form text input (M3), LLM narration (M2), Bevy visual timing (M7), multiplayer synchronization, exhaustive temporal model checking, or real-time guarantees across untrusted remote transports.

## Design questions to resolve before coding
- Exact time units and clock origin; how a host provides elapsed time without drift/duplicate processing.
- Whether the timer starts at presentation-ready acknowledgement or an explicit host command; behavior for reconnecting frontends.
- Interaction boundary precedence and validation for timeout targets/effects.
- Save/restore paused state and offline-time policy, including backward compatibility with v1 saves.
- Whether the first CLI proof uses a manually advanced clock or a real-time host driver; the engine must support deterministic testing either way.

## Deliverables
A focused feature PR with implementation, bounded schema evolution, tests, short replayable demo, compatibility notes, and a decision log for deferred temporal features. Do not merge automatically.

## Implementation and temporal decision log

The [pre-API design](m1.75-design.md) records the decisions; the
[Train authoring/playtesting report](m1.75-playtest.md) records actual play.
No accepted dependency boundary or ADR status was changed. ADR-0006's merged
direction was followed despite its retained Proposed header, as requested.

- World time is optional checked `u64` fictional minutes. Node decision time
  uses positive millisecond budgets and one revision-scoped active observation
  baseline. Host `TimeInput` events, not wall-clock reads, drive core behavior.
- Host elapsed observations precede actions; exact-boundary expiry wins.
  Cumulative observations reject duplicates/regression, and resolution consumes
  the interaction revision. An overrun does not spend a new unseen deadline.
- Ready follows complete prompt availability. Pause freezes, Resume returns to
  AwaitingReady, and both advance revision. In-flight old reads cannot answer a
  scene entered asynchronously; explicit Enter acknowledgement clears the old
  read before activating a new prompt. The real-time CLI uses one standard input
  thread, revision-bound read requests and one monotonic clock source.
- Temporal saves use schema 2 and freeze offline. Active restores as
  AwaitingReady; Paused stays Paused, with exact remaining duration and world
  time. A temporal restore reserves a revision above both saved/current values,
  invalidating pre-save inputs even when loading into a fresh process. Untimed
  schema-1 stories, v1 saves and existing restore behavior remain supported.
- Timeout effects are typed assignments. Targets must be endings or scenes
  with an unconditional effect-free, zero-cost exit to an ending. This narrow
  guarantee avoids arithmetic-blocked expiry or a new general-purpose solver.
- Semantic output exposes only optional remaining time/phase. The adapter emits
  countdown presentation data; renderer and input thread cannot choose outcomes.
  World chronology, timeout effects/targets and clock bookkeeping stay private.
- The bounded checker includes world time in state identity and follows authored
  timeout edges, without enumerating real-time milliseconds or requiring a
  runtime solvability proof. Existing reference story files are unchanged.

| Full reference adventure | 14 authored nodes, two real countdowns, untimed deliberation, multiple fictional costs, evidence/trust/preparation conditions and three explicit endings |
| Every ending/temporal branches | Native full game routes reach all endings; minute-17 vs minute-21 routes have identical evidence/preparation but different controlled-stop availability |
| Authoring checks | Train: 89 states / 130 choices, all three endings and no nonterminal deadlocks found within default bounds; timeout paths included |
| Privacy and compatibility | Temporal projection keys are checked; legacy literal JSON restores; old stories/demos, dependency policy and privacy compile-fail regression remain active |
| Human-style playtest | Actual timely call/platform route with pause/save/load and a complete controlled stop; separate real 15-second silent expiry followed by authored evacuation, including acknowledgement rerun |

Run the README's exact play command and deterministic replay test commands.
The required formatting, Clippy and workspace tests pass (80 tests including the
state-privacy doctest). Real-host tests use short deadlines and bounded waits,
while engine tests use no sleeps or clocks. LSP feedback was clean on some new
files and stale/timed out on others. RustRover file inspections reported no
problems; its build integration could not collect detailed diagnostics. Cargo
checks supply authoritative verification where semantic feedback is unavailable.

Deferred deliberately: offline catch-up, generic scheduling/simulation, dynamic
story generation, NPC planning, network deadline fairness, raw-terminal animation,
provider integration and exhaustive temporal reachability. Finite counter
exhaustion fails without wrapping. Existing live-cycle and bounded-analysis
limitations remain documented, rather than inventing narrative fallback rules.
