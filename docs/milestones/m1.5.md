# M1.5 — World Modeling & Dogfooding

## Goal
Validate GRIMM as a story **authoring tool and playable engine** before M2. Probe the difference between persistent world entities, narrative scenes and story progress, and exercise CYOA-09 without expanding into a world simulator.

## Example
Create a compact independent mystery story (working title: *The Last Lighthouse*): the player investigates a radio message from a vessel that vanished decades ago.

## Authoring and playtest acceptance
- Write the second story **using the current M1 YAML schema first**; do not preemptively modify engine/protocol/renderers.
- Target roughly 10–15 story nodes, at least three explicit endings, conditions/effects, and save/load.
- Show **one named physical/logical location in three separate narrative scenes** (for instance daylight search, night surveillance and next-day return) with distinct authored content, choices and consequences. Revisiting the same graph node is **not** required.
- Reuse a named character across separate scenes; document whether the existing state model suffices for persistent identity and changing relationships.
- Demonstrate at least one meaningful state-dependent decision; verify that returning to a location does not reset story/world progress.
- Test intentional bad endings versus unintended state-dependent deadlocks; refer to [CYOA-09 / issue #4](https://github.com/rjtg/grimm/issues/4). Address the issue in a focused implementation change or document a precisely scoped follow-up if it cannot be safely solved in M1.5.
- Provide scripted tests for each ending and key state-dependent route, an actual CLI playthrough, and a save/load continuation test.
- Produce a short authoring-experience report identifying friction, missing primitives, and the smallest follow-up requirements.

## Implementation guardrails
- M1 nodes already stand for narrative units. Do not rename all nodes to scenes simply for terminology.
- Locations and characters are **conceptual world entities**, not mandatory newly implemented stores in M1.5.
- Only introduce minimal entity/location references or state primitives when a concrete test-story limitation justifies them; document the schema and compatibility implications.
- Preserve the headless core and the engine/adapter/renderer dependency policy; no LLM, NPC planning, ECS, world simulation, graphic frontend or speculative plugin framework.
- An intentionally bad ending must be explicitly authored as an ending; unintended nonterminal deadlocks must not silently masquerade as endings.
- Keep all M0/M1 regression demos passing. Create a reviewable PR; do not merge without review.

## Done when
The independent game is playable, test-covered, and demonstrates the location/scene distinction; CYOA-09 is either resolved with verified acceptance criteria or transparently tracked with evidence from playtesting; the authoring report and documentation are updated.

## Implementation sequence

1. Phase A is recorded separately in the authoring-first commit: 15-node YAML
   adventure and interactive CLI/save-resume playtest, before Rust changes.
2. Phase B found no need for an identity registry or schema extension. Use stable
   visible names, a documented scene mapping and persistent variables; verify
   these conventions with game-specific tests. See the [authoring report](m1.5-authoring-report.md).
3. Phase C adds an opt-in authoring command, `grimm-cli check STORY.yaml`, backed
   by a pure bounded engine traversal from the current session. Default budgets:
   1,024 distinct `(node, variables)` states and 8,192 choice inspections. Explore
   authored routes deterministically, deduplicate exact states to handle cycles,
   report shortest discovered routes to nonterminal no-offer states, and report
   budget exhaustion as **inconclusive**, never a successful validation.
4. Keep one-step executable offers and story/save schemas unchanged. Improve
   runtime blocked-state errors with existing engine validation context. Tests
   cover multi-step effects, cycles, explicit bad endings, save/restore, cutoff
   semantics, Lighthouse routes and the existing regression stories.

This is bounded authoring feedback, not a full solver or a proof that every
route reaches an ending. Cycles with executable moves are not automatically
deadlocks. Revision exhaustion is diagnosed separately from narrative state;
analysis deduplicates node/variable states rather than treating the revision
counter as story progress. No accepted ADR or dependency direction changes.

Local required checks pass: `cargo fmt --check`,
`cargo clippy --workspace --all-targets --locked -- -D warnings`, and
`cargo test --workspace --locked` (55 tests including the state-privacy doctest).
The offline workspace build and bounded checks for both mysteries pass. CI also
executes all four Lighthouse ending scripts in addition to the prior demos.
LSP diagnostics were clean for some new files and stale/timed out for others;
RustRover file inspections reported no problems, while its build tool could not
collect detailed diagnostics. Cargo is the authoritative verification here.

No story/save format migration or entity framework is introduced. The only new
engine surface is the opt-in authoring report/limits API and a pure current-state
diagnostic method. The report is deliberately host-only, never player-visible
semantic output. CYOA-09 is implemented as bounded authoring detection with an
explicit inconclusive result and contextual runtime failure, not a promise of
global solvability or automatic story repair. Remaining limits and a precise
packaging-policy follow-up are in the [authoring report](m1.5-authoring-report.md).
