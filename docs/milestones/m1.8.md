# M1.8 — Narrative Flow & Presentation Gating

## Goal
Make the M1.75 decision deadline fair for actual storytelling: **a timer begins only when required story presentation has finished and offers are available to the player**. Also allow authored narrative-only segments that flow to a successor without forcing an artificial gameplay choice. Both capabilities are engine semantics with host acknowledgements, not renderer-specific rules.

Prerequisites: merged M1.75 Temporal Foundation, ADR-0006, [ADR-0007](../adr/0007-narrative-flow-and-presentation-gating.md) (proposed), existing engine/semantic/adapter/presentation/CLI boundaries and M1.5 scene/entity separation.

## Scope
1. **FLOW-01 — Narrative-only segment:** opt-in authored story format for a segment containing narrative content and an engine-validated successor but no player-facing choice. The engine may continue when explicitly acknowledged that the required presentation finished. Avoid changing ordinary M1 nodes or their existing choice semantics.
2. **FLOW-02 — Presentation completion acknowledgement:** typed renderer/host completion signal correlated to the active scene/presentation revision. It travels via the host/composition root to the engine, not through a direct renderer-to-engine import.
3. **FLOW-03 — Interaction readiness:** a timed scene may require storytelling completion and actual presentation of its choices before `Ready` activates the timer. Specify whether one or two typed acknowledgements are needed and why; **mere output flush must not be treated as player reading**. No timer during narration/voice/camera movement or while choices are unavailable.
4. **FLOW-04 — State, replay and persistence:** engine-authoritative exactly-once non-choice continuation; reject stale and duplicate callbacks; protect against ordering races, automatic loops, invalid successor transitions, revision overflow and interrupted presentations. Persist/reconstruct pending phases on save/load with a clear compatibility policy; pause/resume must not accidentally activate unseen timers.
5. **FLOW-05 — Minimal CLI and mock visual host:** CLI demonstration asks the player to confirm that they finished reading required narration (e.g. Enter) before showing/activating a timed choice. A mock visual renderer reports presentation completion after arbitrarily delayed animation/camera work; the engine neither polls the renderer nor reads a clock.
6. **Playable dogfooding:** add the independent companion adventure **The Silent Signal**, with long untimed storytelling, a genuinely timed decision after readiness, narrative-only progression, investigation and three endings. Preserve all existing reference stories and playthroughs.

## Required acceptance tests
- [x] Node entry, output generation, writing/flushing a prompt and delayed presentation completion do not consume timed-decision budget.
- [x] A timed decision is neither executable while unready nor expired before required presentation completion and offer availability.
- [x] After a valid readiness signal, manually driven elapsed time starts from the full remaining budget; timeout and timely action preserve M1.75 boundary precedence.
- [x] A narrative-only segment advances to its authored successor on completion acknowledgement, without fabricating a `GameAction` or user-visible fake choice.
- [x] Duplicate, stale, future/out-of-order or delayed callbacks never advance a different scene, start a deadline twice or bypass required storytelling.
- [x] Invalid continuation targets/effects, overflow and dangerous auto-advance cycles cannot partially commit or hang the runtime.
- [x] Pause/resume, save/load, disconnect/reconnect and abandoned presentation preserve a coherent pending state, with frozen offline time and deterministic replay.
- [x] Untimed `The Last Witness`, `The Last Lighthouse` and existing `The Last Train` semantics remain compatible by default.
- [x] A host-driven visual-style test can delay presentation arbitrarily without changing world time or deadline and can finish by an acknowledgement.
- [x] An actual CLI playthrough shows text reading acknowledgement, a subsequently activated countdown, a deliberate timeout outcome and narrative-only progression.
- [x] `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, plus existing end-to-end CLI tests pass.

## Design choices to settle during implementation
- Minimal authoring syntax for narrative-only successor and for an interaction that requires presentation completion; how optionality/defaults preserve prior story schema.
- Whether `AwaitingReady` can represent all phases or whether separate presentation-complete and interaction-ready states are needed. Avoid a second timer model.
- Whether a successor should be activated automatically upon acknowledged completion or only after an additional explicit host event; the engine must be sole committer.
- How to correlate acknowledgement with the **current** revision, especially if pause/restore increments revision and a previous renderer finishes later.
- How to handle chained narrative-only nodes and prevent zero-input cycles while permitting valid authored sequences.
- How to reconcile CLI Enter acknowledgement with future timed audio/visual presentations without hard-coding an input device into engine semantics.

## Non-goals
M2 generative narration, free-form input, dynamic graph generation, general animation timelines, Bevy/camera scripting, automatic NPC behavior, wall-clock access from the core, mandatory renderer plugins, generic scheduler or universal entity store.

## Delivery
Feature branch: `feat/m1-8-narrative-flow-gating`. Deliver schema/API documentation,

in a PR against main. Do **not** merge automatically.

## Implementation and acceptance evidence

Player feedback follow-up: the current Silent Signal is version 2 with 14 nodes.
Terminal session controls now live exclusively in an Esc menu, with one-key
Continue/Save/Load/Quit. Opening it pauses via the existing lifecycle; continuing
preserves unread prose and the remaining decision budget. Save/Load use one
checkpoint per story; paused startup saves reopen the menu. Pipe commands remain.
Long required prose now precedes a separate compact timed relay scene; entering
that scene shows choices and activates the deadline immediately. The player no
longer explicitly opens a gated countdown. The generic gated-timed lifecycle is
retained and tested with a dedicated derived fixture; final untimed gating stays
in the game. Terminal choices use a single number key; pipe input stays line-based.
The CLI host alone adds crossterm for key events, with raw-mode restoration and
revision-bound command editing. A Unix real-PTY regression covers these controls.
The original acceptance evidence below describes the initial implementation;
see the playtest report's follow-up for current player-facing behavior.

The [pre-API design](m1.8-design.md) specifies lifecycle transitions and rejected
orderings. [Story-format documentation](../story-format.md) specifies exact YAML,
protocol, persistence and migration. [Authoring/playtesting findings](m1.8-playtest.md)
record actual terminal observations and remaining limitations. ADR-0007 remains
Proposed; no accepted architecture decisions or dependency directions changed.

- Schema 3 adds optional `continue_to` and `presentation_required`. Legacy schema
  1/2 node behavior and save wire shapes remain unchanged. Existing adventures
  are untouched; only default fields were added to prior Rust fixture literals.
- Engine-owned flow uses Presenting → AwaitingInteraction → Interactive, plus
  pause state, and reuses M1.75's single decision deadline model. Completion,
  pause/resume and restore invalidate prior callback revisions. Readiness is a
  separate typed event; duplicate/wrong-order events fail without mutation.
- Typed presentation feedback travels renderer → host → adapter translation →
  FlowInput. The renderer never imports engine types or commits a successor.
  Completion follows explicit CLI reader Enter or a visual renderer's callback;
  printing/flush does not complete required storytelling.
- Narrative-only transitions validate one successor atomically, rejecting bad
  targets, contradictions, revision exhaustion and continuation-only cycles.
  Bounded analysis follows distinct `<continue>` and `<timeout>` diagnostic
  edges using runtime transition previews, retaining cutoff/inconclusive semantics.
- Schema-3 saves persist flow alongside optional existing temporal state.
  Unfinished presentation replays; completed presentation waits for control
  readiness. Paused remains paused. Offline duration is frozen. Restores reserve
  a revision above both current and saved, also for untimed flow stories.
- CLI stale reads cannot complete newer prose or issue lifecycle commands there.
  EOF cannot acknowledge required presentation, including an unterminated blank
  fragment. Active deadlines still expire, stopping at required successor prose
  when closed input cannot supply a genuine completion. No spin or skipped scenes.
