# M1.8 lifecycle design (before API implementation)

Gameplay acceptance follow-up: current adventure version 3 opts `relay` back into
`presentation_required`, alongside `final_gate`. Required reading precedes visible
offers and full-budget readiness in the real playable game, not only a synthetic
test fixture. The lifecycle design below is unchanged; prior version-2 immediate
relay behavior described next is historical and superseded by this acceptance fix.

Player feedback follow-up: the lifecycle below remains intact. Current game
version 2 uses narrative-only buildup followed by a compact ungated timed node,
so entering the decision starts its countdown immediately. CLI terminal input
now uses crossterm key events in the composition root; pipes retain the original
line transport. This supersedes the initial no-new-dependency assumption for the
host only, without changing dependency directions or the canonical model. See
the playtest follow-up and story-format terminal-input section.

Further terminal refinement: Esc opens a host-owned paused session menu; its
single-key actions continue, save/load a per-story checkpoint, or quit. Engine
Pause/Resume and readiness preserve unfinished prose and remaining time. Terminal
colon editing is removed; scripts retain line commands and custom paths.

ADR-0007 remains Proposed. This implements its requested direction without
changing dependency boundaries. No renderer owns story transitions or time.

## Authoring and canonical phases

Story schema 3 adds optional `continue_to: node-id` and
`presentation_required: true` to nodes. A continuation node has content and a
successor, no choices, ending, deadline or additional gate. An interactive gate
has choices and/or a deadline. Both start **Presenting**, with no offers.
Legacy schema 1/2 nodes retain their behavior; schema 3 need not configure time.

`FlowInput { revision, event }` supports PresentationComplete, InteractionReady,
Pause and Resume. Engine-owned `FlowView { phase, paused }` is a visible
coordination projection, not private story state. Phases:

| Current | Input | Result |
|---|---|---|
| Presenting | PresentationComplete | Continuation: commit authored successor once; interactive: AwaitingInteraction, new revision |
| AwaitingInteraction | InteractionReady | Interactive; existing deadline activates at its full remaining duration |
| Any unpaused phase | Pause | Preserve presentation progress, freeze deadline, new revision |
| Paused | Resume | Presenting stays Presenting; other phases return to AwaitingInteraction; new revision |
| Interactive | GameAction / elapsed expiry | Existing atomic engine transition |

All other completion/readiness orderings fail without mutation, including
duplicate completion, readiness before completion, callbacks during pause,
and stale/future revisions. Readiness itself retains the revision, as in M1.75;
phase validation rejects duplicates. Completion consumes a revision even when
staying in the scene, so an early queued ready callback cannot become valid.
Timed gated nodes reuse ActiveDecision, not another timer. TimeEvent Ready,
Pause and Resume delegate to flow for opted-in nodes. Elapsed is still valid
only on an active decision. Explicit world advances are disallowed during flow;
authored action costs retain their normal meaning.

## Continuation safety and diagnostics

Each completion processes exactly one authored edge; the engine never loops
through presentations. Validate targets and contradictory configurations, and
reject cycles composed solely of continuation edges (even if reached through a
choice). Ordinary interactive graph cycles remain supported. Continuations have
no effects or costs in this milestone. Destination immediate playability and
revision capacity are checked before commit. The bounded checker follows a
diagnostic `<continue>` edge, distinct from `<timeout>` and authored choices;
it still explores state-dependent destinations and reports explicit cutoffs.

## Renderer and host

Presentation protocol carries revision-scoped completion requests and interaction
availability, with typed completion/readiness feedback. Text adapter maps semantic
phases to those commands and translates feedback into flow input. Renderer never
imports engine types. Host correlates feedback; engine independently validates.
A mock visual renderer can emit identical feedback after arbitrary external work.

CLI shows required prose then asks for Enter. It does not infer reading from
printing/flushing. Blank Enter completes presentation only, never selects a
choice. Choices appear after completion; renderer reports their availability,
host sends readiness and establishes the existing monotonic observation baseline.
Nonblank lines during required reading do not acknowledge. Session commands still
work, with the existing revision guard before every command. A stale old read is
discarded and cannot acknowledge a newer required segment. EOF during required
presentation exits without completion or fabricated input; EOF on a ready active
deadline continues authored expiry. A new required presentation stops that chain
until genuine acknowledgement; closed input therefore exits. No spin or silent
skipping. Open input waits indefinitely for reading. Legacy prompts stay unchanged.

## Persistence and replay

Schema-3 stories write save schema 3, with optional flow state for the current
node and existing optional temporal state. Schema-1/2 saves/stories retain their
shapes and restore policy. Schema 3 cannot load older saves (new story contract),
and old stories reject schema-3 saves. All restores reserve a revision strictly
above both current and saved for schema 3, including untimed stories.

Pending Presenting restores Presenting: replay that segment in full. Completed
presentation stays completed; Interactive restores AwaitingInteraction. Paused
stays paused; resume cannot complete narration. Timers freeze offline using the
existing remaining duration. Validate phase/node/deadline consistency before
replacement. Acknowledged continuation saves point at the successor, never replay
the previous edge. Record typed lifecycle inputs plus game/time inputs for replay.

No durations, camera/audio controls, automatic completion assumptions, generic
timeline, scheduler or new dependency are introduced. Public Rust DTO literals
need default flow fields; docs will identify wire/schema migration explicitly.
