# M1.75 temporal design (before API changes)

This follows the merged M1.75 brief and ADR-0006's temporal direction. The ADR's
header still says Proposed; this work does not edit its acceptance status or
change any established dependency boundary.

## Model and ordering

- **World time:** optional unsigned fictional minutes, starting at an authored
  origin. Choices have an optional nonnegative `advance_minutes` cost. A candidate
  transition evaluates its own condition before cost/effects, then destination
  conditions after them. Overflow and deadlocks reject the whole transition.
  Nested `world_at_least` / `world_at_most` conditions compare minutes. Real
  hesitation does not advance fictional chronology.
- **Decision time:** a node can declare `decision.limit_ms` and a required
  authored `timeout`. Entering the node creates an AwaitingReady interaction
  with its full remaining duration. Only an explicit revision-scoped Ready input
  activates it. The engine has no clock, sleep, poll or timer thread.
- **Host inputs:** Ready, cumulative Elapsed milliseconds since the latest Ready,
  Pause, Resume, and explicit AdvanceWorld minutes. Each carries the current
  interaction revision. AdvanceWorld is allowed only at untimed nodes and
  commits a new revision after validating the resulting offers. Action costs
  are the normal reference game's world-time driver.
- **Same-instant precedence:** the host submits its elapsed observation before
  a submitted player action. Reaching or exceeding the remaining duration
  commits timeout first; the old action is then stale. A choice before the
  boundary resolves the interaction and makes later old timer inputs stale.
  These are ordered explicit engine inputs, not an engine wall-clock inference.
- **Duplicate handling:** cumulative observations must strictly increase within
  one active interaction. Duplicate/backward observations fail without mutation.
  A timeout changes the revision, so repeating its input cannot resolve twice.
  Ready cannot reset an already active countdown.
- **Pause/resume:** Pause freezes the remaining duration and advances revision;
  Resume advances revision and returns to AwaitingReady. A new Ready starts a
  fresh cumulative observation baseline while preserving remaining duration.
  Actions are rejected while unready or paused. Lifecycle commands for untimed
  nodes fail explicitly. Ordinary untimed M0/M1 actions are unchanged.
- **Readiness and projection:** the host flushes the complete prompt, acknowledges
  Ready, and then starts observing real elapsed time. New interactions never
  inherit an overrun from a previous timer. A slow renderer cannot consume an
  unseen decision's budget. AwaitingReady offers are renderable proposals that
  require readiness before execution; paused interactions show no executable
  choices. Visible output contains remaining time and phase only, never hidden
  world chronology, timeout targets/effects or private temporal bookkeeping.

## Timeout validity and transactional behavior

A timeout is its own authored target plus typed `set` effects. The initial
temporal format deliberately disallows arithmetic timeout effects and world
costs: expiry cannot be blocked by variable/world overflow. Its target must be
an explicit ending, or a scene with an unconditional, effect-free, zero-cost
exit to an ending. That small structural rule guarantees a usable fallback
without a state-space solver. Such scenes may also contain richer choices and
their own independently validated deadline. This supports a lost-call scene
and terminal train consequences without a general scheduler.

Invalid/missing timeout targets, zero/negative durations, incompatible effects,
ending deadlines, and unsupported fallback shapes fail authoring validation.
Each timeout reuses the engine's candidate transition validation before commit.
No partial variables, world cost, timer update or revision commit survives a
failed transition. The usual bounded checker still handles deeper ordinary
story deadlocks; it additionally explores authored timeout edges.

## Persistence and compatibility

- Existing story schema 1 remains accepted with unchanged behavior. Temporal
  features require story schema 2 and an explicit `time` configuration. Old
  untimed nodes/choices default to no deadline and zero fictional cost.
- Existing v1 saves remain readable for untimed stories; untimed games continue
  writing the v1 shape. Temporal games write save schema 2, carrying world
  minutes and optional decision phase/remaining duration. A temporal story
  cannot silently load a v1 checkpoint with missing temporal state.
- Saving is a pure snapshot. The host first accounts for observed active time.
  Saving alone does not pause a running interaction; use Pause before saving
  when desired. Filesystem time while continuing a live session counts normally.
- **Offline policy:** no clock runs while closed. Restore preserves world time
  and remaining milliseconds, maps saved Active to AwaitingReady, and preserves
  Paused. The host must present and acknowledge before counting again.
- Restore validates schema, story identity/version, variable types, world origin,
  decision presence/phase/range and playable state before replacing anything.
  Temporal restores reserve a revision strictly above both the current and saved
  revision (including in a fresh process), and reset observation bookkeeping,
  making old actions, ticks and lifecycle inputs stale. Exhausted revisions
  cannot create an unresolvable timed interaction.
- Provisional Rust struct literals gain defaulted optional fields; migration is
  documented. Legacy serialized semantic outputs omit absent temporal views.
  Presentation gains a countdown command; only the adapter maps semantic timing
  to presentation. No engine/renderer dependency reversal or extra crate.

## Host implementation

Untimed games keep their existing blocking renderer/input path. Temporal games
use one host-owned blocking stdin reader thread and a standard-library channel;
the host loop waits with a bounded timeout and observes one `Instant` clock.
One outstanding read request is bound to its prompt revision. It timestamps
completed lines with that same monotonic clock source and sends
cumulative elapsed events before handling a line and during silence,
so no-input expiry works even with an open stdin. The renderer never chooses
a consequence. If asynchronous expiry changes a scene while its old read is
still pending, that line cannot choose in the new scene. The CLI explicitly asks
for Enter to acknowledge the change; a new deadline remains AwaitingReady until
the old read is discarded and the new prompt is presented. Normal action and
load transitions consume their read before issuing a new revision-scoped one.
Canonical terminal buffering and OS scheduling are not hard realtime guarantees.

EOF releases an obsolete read's acknowledgement barrier and re-presents the
current scene. Active and successive timed prompts still receive readiness and
elapsed observations, allowing all pending authored expiry transitions; EOF on
an untimed or paused prompt exits without a choice. Stale lifecycle commands,
including save/load and quit, are discarded as acknowledgement only, just like
stale choices, so they cannot affect a successor interaction.
The visible indicator refreshes on a
coarse bounded host cadence, while the engine consumes explicit millisecond
observations. `:pause`, `:resume`, `:save PATH`, `:load PATH`, `:quit` are host
lifecycle commands, not free-form game actions. Paused decisions consume no
elapsed time. The host rebuilds adapter mappings after lifecycle/load changes.

## Implementation and acceptance sequence

1. Add versioned temporal authoring/input/save/view types and backward defaults.
2. Add world costs/conditions and pure transactional previews, then revision-
   scoped engine decision/lifecycle inputs. Test with manually supplied times.
3. Extend validation and bounded playability analysis (world time in state keys;
   timeout branches included, no enumeration of every real-time millisecond).
4. Add authored countdown mapping and a small real-time CLI host driver, retaining
   the existing renderer boundary and untimed loop.
5. Author the 10–15-node Last Train with two real deadlines, an untimed opening,
   investigation costs, temporal branches and three explicit endings. Test all
   endings, lifecycle sequences and unchanged prior games.
6. Perform actual CLI playthrough, timely-choice and silent-timeout demonstrations;
   document observations, run required checks, push and open a PR against main.

Deferred: continuous simulation, offline catch-up, arbitrary scheduled events,
NPC planning, network fairness/hard real-time input arbitration, timer animation
frameworks and exhaustive temporal reachability analysis.
