# M3 — Story Authoring & Validation Toolchain

M3 extends the M2 compiler with host-only diagnostics and a semantic story index.
It does not add gameplay primitives, a second compiler, renderer bindings or a
new game. The Locked Room and the untimed detective example remain the demos.

## Commands

Run from the repository root:

```sh
cargo run --locked -p grimm-cli -- check-scene examples/locked-room/story.yaml
cargo run --locked -p grimm-cli -- check-scene examples/locked-room/detective.yaml --json
cargo run --locked -p grimm-cli -- index-scene examples/locked-room/story.yaml > locked-room-index.json
```

`check-scene` prints actionable diagnostics to stderr and a success summary to
stdout. `--json` instead emits a single JSON report to stdout, with diagnostics
and the compiled index. `index-scene` emits just the pretty-printed JSON index on
success; validation errors go to stderr and no partial index is emitted. Its
optional `--json` flag produces a report on validation failure, like check-scene.
No renderer or text/asset manifest is loaded.

Exit codes:

- **0:** compilation and structural checks passed. Warnings/information do not
  fail CI and never assert universal solvability.
- **1:** parse/compile/structural errors, missing/unreadable input, or invalid
  command arguments. File/argument failures are reported on stderr, including
  when `--json` was requested; they are not story-analysis reports.

The commands appear in `grimm-cli --help`. Legacy `check` continues to validate
legacy YAML stories with its existing bounded playability checker.

## Diagnostics

For example:

```sh
cargo run --locked -p grimm-cli -- check-scene crates/cli/tests/fixtures/authoring/normalized-actions.yaml
```

The command exits 1 and reports:

```text
.../normalized-actions.yaml:15:13 (/contexts/0/actions/1/id): error[invalid_scene]: duplicate or reserved action 'room.open_door'
  help: Use distinct normalized IDs; give repeated cue content explicit, distinct cue_id values.
  related declaration: .../normalized-actions.yaml:13:13 (/contexts/0/actions/0/id)
```

Both `Open Door` and `open-door` normalize to `room.open_door`; neither is renamed
or suffixed. Explicit cue IDs and content-derived generated IDs use the exact M2
compiler rules. Duplicate context/namespace declarations and repeated IF guards
also retain their conflicting source paths. Identical narrative content IDs are
legal reusable bindings, not conflicting cue definitions.

Every diagnostic has `severity` (`error`, `warning`, `info`), `code`, `message`, a
`source`, `related` sources and a `suggestion`. A source contains `file`, JSON
Pointer `path` and optional one-based `line`/`column`. The YAML codec resolves
positions using its existing deserializer, including flow YAML, quoting and
comments. If a defaulted/missing field has no source token, the nearest containing
node supplies the position. YAML aliases may point to their anchor; positions
are parser locations rather than editor ranges. Programmatic engine analysis
has source paths but no filename/line until the host supplies them.

Parsing and compilation stop at the first error, using the same validator as
`SceneEngine::new`; they do not manufacture an index from partially normalized
invalid content. Structural analysis collects all findings after compilation.
A JSON report retains its compiled index when structural lint fails, for editor
inspection; the standalone index command still exits nonzero.

## Index contract

The index is versioned (`schema_version: 1`) separately from the story and saves.
Its top level has `story_id`, `story_version` and `contexts`. Each context exposes:

- Effective `id`, `namespace`, `terminal` and its source declaration.
- Qualified `actions`: ID, declaration source and offer usage sources. An
  `available_actions: eligible` instruction references all authored context
  actions; it does not claim all are available in every state.
- `cues`: stable `cue_id`, `generated` flag, optional reusable `narrative_id`,
  and the authored instruction source. No `__run_...` execution occurrences or
  implicit runtime lock/release cues are indexed.
- `narratives`: reusable `narrative_id` and all cue usage sources in that context.
- `transitions`: explicit target context, optional originating action ID,
  `kind` (`action`, `interrupted_action`, `timeout`) and `goto` source.

For example, Locked Room includes the explicit cue definition:

```json
{
  "cue_id": "locked_room.scene_deadline",
  "generated": false,
  "narrative_id": null,
  "source": {
    "file": "examples/locked-room/story.yaml",
    "path": "/contexts/0/cues/1",
    "line": 24,
    "column": 9
  }
}
```

The excerpt above comes from the checked-in story; the exported index is
authoritative after author edits. Contexts, actions, cues and content
bindings are sorted by effective IDs. Transitions and usage references have
stable ordering. Repeated runs with the same source filename and content produce
identical JSON. Moving declarations changes their source paths/positions, but not
explicit IDs or generated IDs derived from the same authored content and timing.
Reordering an explicit offered action list can change its generated cue ID because
that order is authored content. The compiler never reorders executable branches
or cues to achieve index sorting.

External games, renderers or IDEs can compare these identifiers to their own
inventories. GRIMM does not load renderer assets, determine whether an animation
exists, enforce a text inventory or define an asset manifest schema.

## Structural checks and limits

The existing compiler checks references, identifier normalization/collisions,
types, branch/fallback structure, timers, transition instruction rules, start
context, raw structural reachability and presence of an authored terminal.
M3 then inspects the compiled explicit graph:

- A nonterminal with no possible declared transition is an error (`no_exit`).
  An entry plan with neither a possible action offer nor a timer capable of
  invoking a timeout is also a definite dead end (`no_entry_progress`).
- A region with no structural path to any terminal is an error
  (`no_terminal_path`). Successful and failed terminals count equally.
- Fully constant false guards and cases shadowed by fully constant true guards
  produce warnings (`constant_false_action`, `unreachable_branch`). Their
  impossible edges are excluded from structural reachability; unreachable
  contexts are errors (`unreachable_context`).
- Variables and clocks are not treated as constants, even if an initial value
  looks contradictory. Such guarded contexts receive informational
  `state_dependent` diagnostics. A conditional edge is a possible structural
  route, not a proof that the required state can ever occur.
- Cycles are allowed. A cycle with an exit is not classified as a dead end.

No world-state enumeration, exhaustive termination proof, generic SAT solver or
imperative loop syntax is introduced. Availability through particular cue
schedules, effect-dependent satisfiability, elapsed-time feasibility and constant
arithmetic faults are not proved. Constant expressions that cannot be evaluated
are conservatively inconclusive. Authors must still test gameplay routes.

## Compatibility and implementation

Gameplay, M2 YAML, normalized IDs and hash generation, Cue Sheets, action/cue
history, timers and checkpoint serialization are unchanged. Runtime loading uses
the existing compiler checks. Authoring commands are intentionally stricter:
a previously loadable structurally trapped region now fails `check-scene` and
`index-scene`. Regression tests explicitly check that runtime loading remains
compatible. No existing authored story needed modification.

`grimm-semantic::authoring` contains serialized host-only report/index DTOs.
`grimm-engine::scene::authoring::analyze` calls the existing compiler, indexes its
normalized definitions and runs structural analysis. `grimm-cli::authoring`
provides the existing YAML codec, source positioning and command output. The
engine gains no I/O, YAML, JSON, renderer or new package dependency. No accepted
ADR or architectural dependency direction changes.

Source positioning reparses YAML per distinct requested source path (cached within
a report). This keeps it correct for the supported codec without a second parser;
very large stories may justify a measured parser/source-map optimization later.
The report emits one compiler error at a time rather than speculative recovery.
These are current tooling limits, not M4 gameplay features.

## Verification and fixtures

`crates/cli/tests/fixtures/authoring/` contains normalized action collisions,
explicit/generated cue duplicates, missing action/variable/target references,
unreachable contexts, no-exit nodes, trapped regions, cycles with exits, multiple
terminal outcomes, constant-false and state-dependent conditional routes.

The authoring tests cover JSON/exit codes, both conflicting locations,
flow/quoted YAML, type/timer/branch/transition errors, identity stability under
reordering, index agreement with the runtime, reusable narrative bindings and
actual authored examples. Native engine tests keep state/clock checks
inconclusive rather than folding initial values into static facts. Existing M2
CLI playthrough/save tests demonstrate that Locked Room remains playable.

```sh
cargo fmt --all --check
cargo build --workspace --locked
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
```

Final local acceptance: all four commands passed with **137 tests** (124 existing
M0–M2 tests/doctests, 12 authoring integration tests and one native analysis unit
test). Repeated real CLI index exports were byte-identical; Locked Room's scripted
key escape still reached its authored ending. LSP diagnostics were requested;
initial new-file diagnostics were clean, while later bridge requests returned
stale/timeouts, so final semantic verification used the Cargo checks above.
