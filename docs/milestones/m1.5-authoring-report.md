# M1.5 authoring and playtest notebook

## Phase A: existing schema first

`stories/the-last-lighthouse.yaml` was authored and played before changing any
Rust source. At the first terminal playtest, `git status --short` showed only
the new YAML file. The game has 15 nodes, 11 nonterminal scenes and four explicit
endings. It uses only M1 narration/dialogue, typed variables, conditions/effects
and checkpoints. The pre-change CLI loaded it without format changes.

The interactive terminal route was listen to Lena → archive → salvage wire →
record signal → share tape → ask for partnership → answer safely → review
together → publish. It reached **Witnesses on the Shore**. A checkpoint was
written at the night watch with `:save /tmp/grimm-lighthouse-phase-a.json`;
startup `--load` resumed there and reached the same ending. This temporary file
is a local playtest artifact, not a repository fixture.

The first playtest made the choice stakes legible: the archive supplies a
callsign, Lena explains grounding, the tape warns against following the lights,
and the shore scene gives a final, explicit chance to turn back. My author-run
assessment is that this is coherent and atmospheric enough for an initial
external playtest, not independent evidence of player enjoyment. Two lines were
corrected afterward: the opening identifies the recorded woman's voice, and a
return-visit choice no longer asserts that a reply was already heard.

## Phase B: identity, scenes and progress

| Conceptual identity | Authored scenes | Persistent consequences |
|---|---|---|
| `north-spit-radio-room` (North Spit radio room) | `radio_day`, `radio_night`, `radio_return`; also `final_watch` | Callsign knowledge, recorded evidence, wire and transmitted reply survive the night/dawn scene transitions |
| `lena-voss` (Lena Voss) | Opening, `lena_day`, night watch, `night_confession`, dawn return and final decision | `lena_trust` changes access to partnership, joint review and public investigation |

These identities are authoring conventions, not engine entity records. YAML
comments document the mapping; repeated visible names and consistent dialogue
establish identity for players. Three separate node IDs represent three distinct
situations at one place; the node ID never stands for the physical location.
Story progress belongs to variables, not the place name. The same dawn scene has
different offers depending on the night's accumulated state.

**Decision: no entity/schema extension.** Existing primitives suffice for this
compact authored adventure, so adding reference fields or a registry would not
solve an observed blocker. This is consistent with accepted ADR-0005. It does
not demonstrate machine-enforced identity consistency: spelling and continuity
still need editorial review and game-specific tests. A future story requiring
automated reference validation can supply evidence for a small identity feature;
a universal store, ECS and world simulation remain unjustified here.

## Actual friction and recommendations

- **No conditional content blocks.** Changed relationships appear in choice
  labels/availability; a substantially different spoken response would require
  another scene. That worked here without duplicating a whole graph. Revisit
  small conditional authored-content support only with a concrete story need.
- **Identity is editorial.** Names, the YAML identity map and tests keep the
  location/character consistent. A typo is not a schema error today.
- **State declarations are verbose.** The five narrowly named variables were
  manageable. There is no need for nested entity state just to shorten effects.
- **Numbered routes change with state.** Test semantic choice IDs as well as
  actual CLI number sequences. This caught a scripted run that stopped one input
  short of the final decision; EOF was correctly not a win.
- **CLI repeats the scene after saving.** Save/resume works, but reprinting long
  prose is noisy. A future presentation-only improvement could reprint just the
  prompt after host commands. It must not change canonical state.
- **One-step previews do not prove later playability.** CYOA-09 needs authoring
  diagnostics across several transitions. Keep this separate from presentation
  and preserve immediate offer/application consistency.

Later milestones should be driven by an observed authoring problem, not by
retrofitting these scenes into entities or introducing a second progress graph.
